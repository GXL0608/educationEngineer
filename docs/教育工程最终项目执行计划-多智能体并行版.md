## 2. 根本定义与八个总决策

1. 当前项目不是独立平台，而是外部平台中的一个“教育工程 Web 功能模块”。
2. 外部平台负责账号、支付、壳子、分发和整体平台能力；当前项目不自建这些能力。
3. 当前项目必须最终发布给真实用户使用，因此所有计划必须以“可上线、可维护、可扩张、可评估”的产品标准来制定。
4. 当前项目的唯一交付主形态是 Web 网页端，以响应式网页和 WebView 嵌入为唯一主线。
5. 桌面端和移动端都通过网页嵌入方式套壳，必须保证同一套 Web 代码在浏览器、桌面壳子和移动壳子里一致运行。
6. 总体业务目标不是做几个试验性功能，而是建设一个最终可覆盖 K12、本科、硕士、博士各层级课程、教材、知识点、题目、试卷、文献与研究材料的教育工程系统。
7. 一期首发版允许聚焦高价值场景，但顶层架构、内容模型、页面体系、功能模块和数据模型必须从一开始就按“全量覆盖目标”设计。
8. 一期组织路线固定为“人类领导者 + 层级总控 + 黑板任务队列 + 验证者分离 + 外部记忆标准件”，扩张目标先打透 8-12 个 agent 稳定协同。

## 3. 最终产品定义

### 3.1 产品本质

教育工程的最终形态不是单个课程播放器，也不是普通题库，也不是普通 AI 对话工具。它是一个面向所有学习层级的“知识理解、认知增强、题目训练、考试准备、文献研读、研究支持”的统一 Web 教育系统。

### 3.2 产品必须同时满足四个属性

1. 它是一个真实发布的用户产品，必须有明确页面、完整交互、稳定体验和上线质量。
2. 它是一个可扩张的内容系统，必须能承载全学段、全学科、全教材、全题型、全文献类型。
3. 它是一个认知增强引擎，必须通过视听同步、结构化可视化、主动回忆和反馈回流提升理解与记忆效果。
4. 它是一个工程化生产系统，必须通过组件化、脚本化、内容工厂化和多智能体协同实现持续扩张。

### 3.3 用户层级

最终系统覆盖以下用户层级：

- K12 学生
- 大学生
- 硕士研究生
- 博士研究生
- 自学者
- 考试备考用户
- 研究型用户

### 3.4 用户目标

用户在系统中要完成的核心任务包括：

- 找到对应年级、专业、课程、教材和章节
- 用多模态方式理解复杂内容
- 对知识点进行结构化掌握
- 训练习题、真题、模拟题和试卷
- 记录错题、笔记、卡片和知识链
- 完成复习、巩固和间隔强化
- 进行文献精读、论证拆解和研究支持

## 4. 范围模型：总范围、首发范围、长期范围

### 4.1 总范围

最终目标范围包括：

- K12 全学段课程、教材、章节、知识点、题目、试卷
- 大学公共基础课与专业核心课程
- 硕士课程、研究方法、专业方向课程
- 博士课程、资格考试、前沿文献、研究设计支持
- 教材、讲义、辅导资料、真题、模拟题、文献、研究报告等多内容类型

### 4.2 首发范围

首发版仍需聚焦，否则无法交付。首发版聚焦三类高价值能力：

- 复杂文本精读
- 复杂概念讲解
- 文献与研究材料精读

但首发版的内容模型和页面结构必须直接支持后续扩到：

- 题库训练
- 试卷考试
- 错题复盘
- 全学科目录
- 学段与专业切换
- 教材版本切换

### 4.3 长期范围

长期范围不是一句“未来再说”，而是当前计划必须预埋的目标：

- K12 全主科与综合科目
- 大学公共课和主要学科门类
- 硕士与博士课程体系
- 研究型工作流
- 大规模教材版本与考纲版本管理

## 5. 全学段全内容覆盖蓝图

### 5.1 覆盖原则

要支持 K12、本科、硕士、博士所有课程、教材、考题，不能靠“功能堆叠”，必须先建立统一内容宇宙模型。

### 5.2 统一内容宇宙模型

所有内容都统一落入以下层次：

| 层级 | 对象 | 说明 |
| --- | --- | --- |
| L0 | 学段 | K12 / 本科 / 硕士 / 博士 |
| L1 | 学科域 | 数学、语文、英语、物理、化学、计算机、法学、医学等 |
| L2 | 课程 | 高中物理、微积分、数据结构、细胞生物学、研究方法等 |
| L3 | 版本与体系 | 课程标准、教材版本、院校 syllabus、考纲版本 |
| L4 | 结构单元 | 章节、单元、专题、模块、实验、主题 |
| L5 | 知识单元 | 概念、定理、公式、方法、模型、术语、论点 |
| L6 | 学习资产 | 讲解脚本、导图、图谱、例题、题目、试卷、文献、笔记 |
| L7 | 交互资产 | 音频、图形、时间轴、练习、回忆卡、错题卡、反馈记录 |

## 6. 页面体系与发布级体验要求

### 6.1 页面设计总要求

由于最终产品要发布给真实用户，页面必须满足以下硬要求：

- 信息结构清楚
- 主任务突出
- 页面层级明确
- 视觉风格统一
- 排版精致
- 移动端和桌面端都易用
- 不堆砌花哨元素
- 动效服务于理解，不制造噪音

### 6.2 体验设计原则

1. 内容优先：页面首先服务理解，不服务炫技。
2. 认知聚焦：每个页面只突出当前最重要任务。
3. 清晰层级：标题、正文、结构图、提示、反馈必须有明确优先级。
4. 节奏控制：高亮、音频、结构图变化要服从时间轴。
5. 跨端一致：Web 浏览器、桌面壳子、移动壳子中的核心流程必须一致。
6. 美观但克制：界面要精致、清爽、现代，不做教育软件式陈旧设计。

### 6.4 页面视觉要求

页面必须达到以下质量标准：

- 有一致的设计 token：颜色、字体、间距、圆角、阴影、动效
- 阅读页必须具备高级排版能力，而不是普通后台表格式页面
- 图谱、逻辑链和时间线必须是产品级视觉，不是开发调试图
- 移动端必须重排而不是简单缩小
- WebView 中字体、触控、滚动和输入体验必须稳定

### 6.5 页面验收标准

每个页面上线前必须经过：

- 产品验收
- 设计验收
- 前端回归
- WebView 回归
- 性能验收
- 可用性走查

## 7. 功能模块蓝图

### 7.1 模块设计原则

教育工程不能停留在“认知增强”概念上，必须具体化为可交付模块。每个模块都必须回答五个问题：

1. 用户在这个模块里完成什么任务。
2. 这个模块如何增强理解、记忆、推理或研究。
3. 这个模块依赖哪些内容中间表示和预制组件。
4. 这个模块如何被 Web 页面呈现，并适配桌面和移动端壳子。
5. 这个模块的效果如何被验证。

### 7.2 用户侧核心功能模块

用户层基于此展开：

- `M3 精读阅读器`、`M4 概念讲解画布`、`M9 文献研读工作台` 直接建立理解能力
- `M5 练习训练引擎`、`M6 试卷考试引擎` 建立训练与测试能力
- `M7 错题与复习系统`、`M8 笔记与知识卡片` 建立强化和长期记忆能力
- `M10 学习路径与报告`、`M11 搜索与发现`、`M12 个体反馈系统` 建立长期使用能力

## 8. 教材、题库、文献与内容工厂计划

### 8.1 为什么必须先做内容工厂

如果没有统一内容工厂，所谓“支持所有课程、教材、考题”会迅速失控。要支撑全量覆盖，必须先做内容生产流水线，而不是靠人工逐页堆内容。

### 8.2 内容接入对象

系统需要支持以下内容对象：

- 教材正文
- 讲义与课件
- 章节知识点目录
- 例题与习题
- 真题与模拟题
- 整卷试卷
- 论文与研究报告
- 图表与实验材料

### 8.3 内容处理流水线

统一内容流水线固定为：

`原始资料 -> 切片 -> 结构化 -> 知识点挂接 -> 脚本生成 -> 组件装配 -> 用户运行 -> 数据回流 -> 脚本与组件优化`

### 8.4 内容运营策略

内容扩张按四层推进：

1. 核心标准层：
   - 建课程树
   - 建章节树
   - 建知识点树

### 8.5 内容版权与治理

由于产品面向用户发布，内容必须区分来源和权限：

## 9. 总体技术选型

### 9.1 交付形态

一期固定为“可嵌入 Web 模块”：

- 标准浏览器中可直接访问
- 桌面壳子通过 WebView 或内嵌浏览器加载同一地址
- 移动壳子通过 WebView 加载同一地址
- 外部平台通过 URL、Token、`postMessage` 或 JS Bridge 完成宿主集成

结论是：不做 Electron、React Native、Flutter 三套并行前端，不做多端各自独立开发，只做一套 Web 主代码。

### 9.2 前端主栈

| 层级 | 选型 | 选择理由 |
| --- | --- | --- |
| 基础框架 | React 19 + TypeScript 5 | 生态成熟，适合复杂交互和组件化预制件体系 |
| 构建工具 | Vite 6 | 启动快、构建快，适合独立 Web 模块和多环境嵌入 |
| 路由 | TanStack Router | 类型安全、数据路由清晰，适合模块化页面和嵌入场景 |
| 数据请求 | TanStack Query | 适合缓存、重试、预取和实验开关控制 |
| 本地状态 | Zustand | 轻量，适合播放器状态、脚本状态、嵌入桥接状态 |
| 样式系统 | Tailwind CSS 4 + CSS Variables | 统一设计 token，兼顾快速搭建与主题适配 |
| 可访问性基础 | Radix UI | 提供可访问组件底座，避免重复造轮子 |
| 组件文档 | Storybook | 用于预制组件审查、回归和设计对齐 |
| 测试 | Vitest + Testing Library + Playwright | 单测、交互测、端到端测试闭环 |

### 9.3 Web 交互与多模态技术

| 能力 | 选型 | 用途 |
| --- | --- | --- |
| 富文本与段落渲染 | Markdown AST + 自定义渲染层 | 用于精读内容分段、高亮、术语标注、结构提示 |
| 音频播放 | Howler.js + Web Audio API | 用于 TTS 播放、精确暂停、音频进度与文本同步 |
| 语音时间轴 | 自定义 `script.json` 时间码协议 | 用于句级、词级同步高亮和节奏控制 |
| 图谱/流程/逻辑链 | React Flow + ELK.js | 用于概念关系、逻辑链、流程图、知识路径展示 |
| 高密度图关系 | Cytoscape.js | 用于文献关系图、知识图谱和节点探索 |
| 图表与时间线 | ECharts | 用于时间线、散点图、进度图和统计可视化 |
| 动效 | Motion | 用于节奏化切换、聚焦、渐显和弱动效引导 |
| 音视频字幕叠层 | 原生 HTML5 Video + 自定义 overlay 层 | 用于讲解视频或演示叠加 |

### 9.4 服务端与 AI 处理层

一期建议采用“TypeScript BFF + Python AI 服务”的双层方案：

| 层级 | 选型 | 职责 |
| --- | --- | --- |
| BFF / 应用 API | NestJS + TypeScript | 提供 Web 模块 API、宿主集成适配、配置、内容会话、反馈接收 |
| AI / 处理服务 | FastAPI + Python 3.12 | 负责内容解析、脚本生成、可视化中间表示、评估任务、AIGC 调优 |
| 异步任务 | BullMQ + Redis | 负责脚本生成、音频生成、评估任务、artifact 处理 |
| Agent Harness | 独立 Runner + 文件化外部记忆 | 负责多智能体任务流、进度交接、验证与回滚 |

### 9.5 数据与存储

| 能力 | 选型 | 用途 |
| --- | --- | --- |
| 主数据库 | PostgreSQL 16 | 存课程、教材、章节、知识点、题目、反馈、任务状态 |
| 语义检索 | pgvector | 存知识切片、术语向量、文献段落向量 |
| 全文搜索扩容层 | OpenSearch | 用于大规模教材、题目、文献检索的长期扩容 |
| 缓存与锁 | Redis | 存队列、播放器会话、任务锁、短期缓存 |
| 文件存储 | S3 兼容对象存储 | 存音频、截图、图谱快照、实验工件、日志产物 |
| 可观测性 | OpenTelemetry + Grafana + Loki | 存 trace、日志、错误、关键播放指标 |

### 9.6 宿主平台嵌入协议

外部平台是宿主，教育工程模块必须提供稳定宿主协议。建议一期固定以下接口：

- 宿主输入：
  - `hostUserToken`
  - `hostUserId`
  - `hostTheme`
  - `hostLocale`
  - `hostDeviceType`
  - `hostCapabilities`
- 模块输出事件：
  - `lesson_started`
  - `lesson_progress_changed`
  - `lesson_completed`
  - `feedback_submitted`
  - `checkpoint_saved`
  - `exception_raised`
- 通讯方式：
  - 浏览器环境优先使用 HTTPS API
  - WebView/iframe 嵌入优先使用 `postMessage`
  - 必要时通过 JS Bridge 暴露少量宿主能力

### 9.7 测试、发布与兼容策略

- 浏览器兼容目标：Chrome、Safari、Edge 最新两个稳定版本
- WebView 兼容目标：iOS WKWebView、Android System WebView、桌面 Chromium 壳子
- 页面形态：响应式布局，优先覆盖 390px 到 1440px 宽度
- 发布策略：灰度发布、实验开关、场景级回滚
- 回归方式：Storybook 组件回归 + Playwright 场景回归 + benchmark 指标回归

### 12.2 扩容规则

1. 第 1-4 周采用 4-6 agent 轻编组，验证任务卡、黑板队列和外部记忆格式。
2. 第 5-14 周扩到 8-12 agent，形成标准编组。
3. 第 15-24 周扩到 12-16 agent，覆盖内容工厂、题库工厂和 Web 主线。
4. 第二阶段才做 16-32 agent 受控实验。
5. 100/500 agent 不进入真实主线开发，只进入离散事件仿真和抽样压测。

### 12.3 任务流规则

1. Human Principal 只下达周目标、边界和禁止区，不直接指挥每个微任务。
2. A0 把周目标拆成任务卡，写入黑板队列。
3. 经理类 agent 只负责路由、拆解、优先级和依赖，不直接做大规模实现。
4. 执行类 agent 必须在隔离工作区内完成任务，并提交结构化产物。
5. A11 独立验证质量、测试、指标和实验结果，不参与原任务实现。
6. A12 监控预算、权限和合规，必要时直接阻断任务。
7. A13 在每个工作日收口，更新外部记忆并压缩上下文。
8. 未通过验证的产物不得进入主发布分支。

program/PAGE_MAP.md
program/COMPONENT_CATALOG.md
program/QUESTION_BANK_MODEL.md
program/SKILL_REGISTRY.md
program/RUNBOOK.md
program/PROGRESS.md
program/RISK_LOG.md
program/FEATURE_LIST.json
program/BENCHMARKS/
program/ARTIFACTS/

- `SKILL_REGISTRY.md`：写 Skill 名称、触发条件、版本、评测集
- `RUNBOOK.md`：写运行规则、常用命令、异常处理和回滚
- `PROGRESS.md`：写今日进展、阻塞、下一步、升级点
- `RISK_LOG.md`：写范围、质量、成本、合规、进度风险
- `FEATURE_LIST.json`：写功能完成状态、验证状态、发布状态
- `BENCHMARKS/`：放任务集、对照实验、trace grading 规则
- `ARTIFACTS/`：放截图、日志、报表、原型、发布物

## 20. 周节奏与复盘制度

### 20.1 每周固定节奏

1. 周一：Human Principal 定目标，A0 拆任务，冻结本周禁止区。
2. 周二到周三：各泳道并行推进，执行类 agent 只做已领任务。
3. 周四：A11 跑验证，A12 做风险与成本检查，A13 汇总文档与 progress。
4. 周五：做里程碑审阅、队列清理、上下文压缩、下周假设更新。

### 20.2 每周必须复盘的内容

- 模型与工具变化是否影响 Skill 触发和调度效果
- benchmark 是否退化
- 哪些任务是假并行，哪些任务可以继续拆细
- 是否出现上下文漂移、重复劳动、验证堵塞
- 哪些组件复用率低，需要下线或重构
- Web 模块在桌面壳子和移动壳子中是否出现兼容回退
- 页面是否出现理解障碍、流程割裂或设计退化
- 内容工厂、题库工厂、文献工厂哪一段成为瓶颈
- 成本、时延、人工干预次数是否异常

## 21. 风险与治理

1. 范围失控：通过总范围/首发范围双层冻结表控制，未经放行不得新增首发任务。
2. 多模态过载：所有新交互必须经过认知负荷审查，不符合“增强理解”的设计直接打回。
3. 假并行：通过任务卡、任务锁、黑板领取机制和 verifier 分离降低重复劳动。
4. 上下文漂移：强制使用 `PROGRESS.md`、`RUNBOOK.md`、`FEATURE_LIST.json` 和日终压缩。
5. 外部平台集成反向绑架主线：账号、支付、壳子能力不进入当前项目主线，教育工程模块只对接宿主协议。
6. WebView 兼容风险：所有关键功能必须经过浏览器和 WebView 双通道回归。
7. 设计退化风险：所有页面必须经过设计系统校验，禁止出现临时拼装风格。
8. 内容扩张失控：没有进入统一内容宇宙模型的教材、题库和文献不得直接上线。
9. AIGC 质量波动：关键内容必须经过人工或 verifier 审查，不允许未审自动上线。
10. 成本失控：A12 设预算守门规则，超过阈值自动降并行或切换较小模型。
11. 权限和合规风险：涉及版权、隐私、未成年人内容和宿主桥接能力时强制人工放行。
12. 人类过载：人类只处理目标、边界、异常和放行，不重新接管全部微任务。

## 22. 最终验收标准

项目在首发版结束时，必须同时满足以下条件，才视为完成：

1. 首页、导航页、课程页、教材页、精读页、概念页、练习页、试卷页、错题页、文献页、报告页、搜索页都具备可上线质量。
2. Web 模块能在浏览器、桌面壳子和移动壳子中稳定运行。
3. 复杂文本精读、复杂概念讲解、文献精读、基础练习、基础试卷、错题复盘都能端到端跑通。
4. 课程宇宙、内容模型、题库模型、页面系统、组件库、Prompt/Skill 规范、嵌入协议、runbook、合规包全部成文。
5. 组件库能够支撑跨场景复用，复用率达到目标。
6. 8-12 agent 协同流程稳定，且有不少于 4 小时自治运行记录。
7. benchmark、A/B 或对照实验、trace grading、周度复盘机制全部跑通。
8. 风险、预算、权限、回滚和发布机制可审计、可复盘、可继续扩张。

## 23. 结语

这份计划的核心不是把概念写得更大，而是把“大愿景”压缩成“可被真实发布、可被 8-12 个 agent 并行建设、可被 verifier 验证、可被人类治理、可在 24 周交付首发版并在 36 个月扩到全量版”的系统工程。

当前项目不是再造一个大平台，而是做一个真正能嵌入平台、能在桌面和移动壳子中稳定运行、能承载全学段全学科内容扩张、能把教材/题目/试卷/文献转成教程单元并产生认知增强效果的 Web 教育工程模块。

首发版真正要打透的不是几个零散功能，而是六件事：

1. 页面体系是否达到真实发布标准
2. 教程与认知增强引擎是否成立
3. 题库与试卷系统是否成立
4. 内容工厂和组件路线是否成立
5. Web 嵌入与跨端兼容是否成立
6. 多智能体交付方式是否成立

只要这六件事成立，系统就具备从首发版向 K12、大学、硕士、博士全量教育工程扩张的真实基础。
